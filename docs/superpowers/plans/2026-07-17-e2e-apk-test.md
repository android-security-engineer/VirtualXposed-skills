# 端到端 APK 测试流程 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: 内联执行（用户要求"你来跑一下，直到这个流程能够跑通"，不外派 subagent，自行迭代修复）
> Steps use checkbox (`- [ ]`) syntax.

**Goal:** 跑通完整端到端流程：CI 构建 → 推 tag 触发 release → 下载 release APK → 在云手机（Android 13 redroid13_x86_64）上安装 → 启动验证。发现的问题就地修复，循环重跑直至流程跑通。

**Architecture:** 本地改 release.yml（补未签名降级）+ VirtualApp MethodProxies（修 Android 13 Long 拆箱崩溃）→ push 触发 android.yml CI 验证构建通过 → 推 `v*` tag 触发 release.yml 发布 GitHub Release（无签名 Secret 时走降级产未签名 APK）→ 本地 `gh release download` 拉 APK → 本地用 test.jks (apksigner) 对未签名 APK 签名 → `adb install` 装到云手机 → `am start` 启动 → `adb logcat` 捕获结果。若启动崩溃，定位下一处、修复、重打 tag/重装，循环。

**Tech Stack:**
- CI: GitHub Actions（android.yml 构建 / release.yml tag 触发发布），actionlint 本地校验
- 构建: AGP 3.2.1 / Gradle 4.6 / NDK r19c（已跑通的老栈，见 memory `vxp-ci-android-legacy-stack-gotchas`）
- 签名: 本地 `~/android-sdk/build-tools/34.0.0/` 的 zipalign + apksigner（V1+V2+V3），keystore `/tmp/vxp-e2e-probe/test.jks`（PKCS12, RSA-2048, alias=vxp-test, pass=virtualxposed）
- 验证设备: 云手机 `192.168.1.90:5555`，Android 13 / SDK 33 / x86_64 / redroid13_x86_64（**超出 VirtualXposed 官方支持范围 5.0~10.0**）
- 目标 APK: `app-aosp-release`，applicationId `io.va.exposed64`，versionName 0.22.0，启动 Activity `io.virtualapp.splash.SplashActivity`

**Risks:**
- **VirtualApp 只读约束冲突（核心设计决策）**：CLAUDE.md 明确"不要改 `VirtualApp/` 源码，它是只读参考本体"。但用户本次会话明确指令"发现问题就修复，重新进行这个流程，直到这个流程能够跑通"，指令优先级高于文档约定。缓解：仅做单点最小兼容性修复（`(int)→((Number)…).intValue()`），commit message 与本计划记录理由，绝不顺手重构或扩大改动面。
- **Android 13 超出官方支持范围**：VirtualXposed 官方支持 5.0~10.0，云手机是 13 (SDK 33)。即使修了 `MethodProxies:635`，后续 AMS/PMS/隐藏 API/SELinux 可能连环崩溃。缓解：每修一处就重新部署验证；若进入"修一个崩一个"的连环模式，止步并如实记录"运行层超出支持范围"，但**流程层（CI/release/下载/安装）跑通即算本计划达成**。
- **release.yml 降级产出未签名 APK，Android 13 拒绝安装**：`INSTALL_PARSE_FAILED_NO_CERTIFICATES`。缓解：本地用 test.jks 对下载的 release APK 二次签名（上一周期已验证此流程可行）。
- **tag 触发不可逆且污染 release 历史**：测试 tag 会产出公开 Release。缓解：用 `v0.22.0-e2e-test1` 这类明确标注 `e2e-test` 的 tag，验证后可删；优先用 `workflow_dispatch` 手动触发而非 push tag。
- **无正式 release keystore Secret**：4 个签名 Secret 未配置（见 memory `vxp-release-signing-secrets`）。缓解：本计划全程走未签名降级 + 本地二次签名，不依赖 Secret。

### Task 1: 修复 release.yml 未签名降级 — 让 tag 触发的 release 在无签名 Secret 时也能产出 APK

**Depends on:** None
**Files:**
- Modify: `.github/workflows/release.yml`（"Decode release keystore" step，移植 android.yml 的 env-based 降级写法）
- Modify: `.github/workflows/release.yml`（Release body 文案，补未签名降级说明）

- [ ] **Step 1: 修改 Decode step 为 env-based 降级 — secret 为空时跳过签名产出未签名 APK**
文件: `.github/workflows/release.yml` 的 "Decode release keystore" step（当前无降级，secret 为空会产出空 .jks 导致 gradle 崩）

```yaml
      - name: Decode release keystore
        env:
          KS_B64: ${{ secrets.VXP_KEYSTORE_BASE64 }}
          KS_ALIAS: ${{ secrets.VXP_KEY_ALIAS }}
          KS_KEY_PWD: ${{ secrets.VXP_KEY_PWD }}
          KS_STORE_PWD: ${{ secrets.VXP_STORE_PWD }}
        run: |
          if [ -z "$KS_B64" ]; then
            echo "VXP_KEYSTORE_BASE64 未配置，跳过签名，产出未签名 APK（降级模式）。"
            exit 0
          fi
          echo "$KS_B64" | base64 -d > VirtualApp/release.jks
          echo "keystore.path=release.jks" > VirtualApp/local.properties
          echo "keystore.alias=$KS_ALIAS" >> VirtualApp/local.properties
          echo "keystore.pwd=$KS_KEY_PWD" >> VirtualApp/local.properties
          echo "keystore.alias_pwd=$KS_STORE_PWD" >> VirtualApp/local.properties
```

**理由**：android.yml 已验证此模式可行（见 memory `vxp-ci-android-legacy-stack-gotchas` 坑 1：secret 不能进 `if:` 条件，必须经 `env:` 传入 shell 内判断）。release.yml 当前直接 `echo "${{ secrets.X }}" | base64 -d`，secret 为空时产出 0 字节 .jks，gradle 构建必崩。

### Task 2: 修复 MethodProxies.java:635 Android 13 Long 拆箱崩溃 — 让服务器进程能启动

**Depends on:** None（与 Task 1 并行，无文件冲突）
**Files:**
- Modify: `VirtualApp/lib/src/main/java/com/lody/virtual/client/hook/proxies/pm/MethodProxies.java:635`（`GetPackageInfo.call` 的 `(int) args[1]`）

- [ ] **Step 1: 修改 GetPackageInfo.call 第 635 行 — 兼容 flags 为 Long 的新 Android**
文件: `VirtualApp/lib/src/main/java/com/lody/virtual/client/hook/proxies/pm/MethodProxies.java:633-648`（`GetPackageInfo.call` 方法）

```java
        @Override
        public Object call(Object who, Method method, Object... args) throws Throwable {
            String pkg = (String) args[0];
            int flags = ((Number) args[1]).intValue();
            int userId = VUserHandle.myUserId();
            PackageInfo packageInfo = VPackageManager.get().getPackageInfo(pkg, flags, userId);
            if (packageInfo != null) {
                return packageInfo;
            }
            packageInfo = (PackageInfo) method.invoke(who, args);
            if (packageInfo != null) {
                if (isVisiblePackage(packageInfo.applicationInfo)) {
                    return packageInfo;
                }
            }
            return null;
        }
```

**理由**：Android 13 (SDK 33) 的 `IPackageManager.getPackageInfo` 把 `flags` 参数从 `int` 改为 `long`，反射 invoke 时 `args[1]` 装箱成 `Long`。原代码 `(int) args[1]` 对 `Long` 拆箱直接抛 `ClassCastException: Long cannot be cast to Integer`，崩溃堆栈：`MethodProxies$GetPackageInfo.call:635` ← `MethodInvocationStub$HookInvocationHandler.invoke:186` ← `VActivityManagerService.onCreate:116` ← `systemReady:98` ← `BinderProvider.onCreate:46`。`(Number).intValue()` 对 Integer/Long 都安全。

**注意**：文件中另有 17 处 `(int) args[N]`（见调研 grep），但本步**仅修实际触发崩溃的 635 行**，不顺带改其它——避免引入未验证变更。后续若其它方法在启动路径上崩溃，再逐个修。

- [ ] **Step 2: 提交**
Run: `git add VirtualApp/lib/src/main/java/com/lody/virtual/client/hook/proxies/pm/MethodProxies.java && git commit -m "fix(pm): GetPackageInfo flags 用 Number.intValue() — 兼容 Android 8+ flags 为 long 的 ClassCastException

服务器进程 io.va.exposed64:x 在 Android 13 启动即崩：
MethodProxies\$GetPackageInfo.call:635 (int)args[1] 对 Long 拆箱失败。
改用 ((Number)args[1]).intValue() 兼容 Integer/Long。
注：VirtualApp/ 原为只读参考，本修复为端到端测试必要兼容性修复。"`

├─ 有 PID（存活） → 流程跑通 ✅ 清理测试 tag，完成
